Four compose files describe the demonstration environment served under `openfsp.org`. Each one is deployed as its own
[Coolify](https://coolify.io) service and reaches the others over their public addresses only:

- [`gateway/compose.yaml`](gateway/compose.yaml): the gateway, which serves its console.
- [`simulator/compose.yaml`](simulator/compose.yaml): the simulator of the MonCash, NatCash and OpenFSP providers, which
  serves its interface.
- [`validator/compose.yaml`](validator/compose.yaml): the conformance validator, which serves its interface.
- [`demo/compose.yaml`](demo/compose.yaml): the demonstration shop of [openfspht/demo](https://github.com/openfspht/demo).

The first three run the images of [openfspht/openfsp](https://github.com/openfspht/openfsp), one process per service.
The gateway serves the `test` environment and reaches simulated payment services only.

## Services

| Service | Stack | Address |
|---|---|---|
| `shop` | `demo` | https://demo.openfsp.org |
| `gateway` | `gateway` | https://gateway.openfsp.org, https://console.openfsp.org |
| `postgres` | `gateway` | internal |
| `simulator` | `simulator` | https://simulator.openfsp.org |
| `validator` | `validator` | https://validator.openfsp.org, https://l.openfsp.org (attestation short links) |
| `postgres` | `validator` | internal |

Coolify maps each address to its service on its container port: `8080` for the gateway, `8090` for the simulator, `8095`
for the validator. The addresses are `A` records of the `openfsp.org` zone. The gateway serves the console and `/admin`
on `console.openfsp.org` only (`OPENFSP_ADMIN_HOST`) and answers 404 for them on `gateway.openfsp.org`. The simulator
interface and its API share `simulator.openfsp.org`; the interface acts as the published `mock_openfsp` account, whose key
stays on the server.

## Variables

These values are set on the Coolify services and never committed. Every one of them is required.

| Variable | Stack | Content |
|---|---|---|
| `SERVICE_PASSWORD_POSTGRES` | `gateway`, `validator` | Database password, generated by Coolify |
| `OPENFSP_APP_KEY` | `gateway` | Application key, `openssl rand -base64 32`, kept stable: replacing it signs out administrators, makes the stored merchant credentials and webhook signing keys unreadable and invalidates the callback URLs of pending payments |
| `OPENFSP_TRUSTED_PROXIES` | `gateway` | Address of the Traefik container on the Coolify network, the only peer whose forwarded headers are read; without it every client shares the proxy address in the rate limits |
| `OPENFSP_VALIDATOR_ATTESTATION_SIGNING_KEY` | `validator` | Ed25519 private key in PKCS#8 PEM that signs the attestations, `openssl genpkey -algorithm ed25519`, mounted as a file |
| `SENTRY_DSN_BACKEND`, `SENTRY_DSN_FRONTEND` | `gateway`, `simulator`, `validator` | Sentry DSN of the services and of their interfaces (`OPENFSP_UI_SENTRY_DSN`) |
| `SENTRY_DSN_DEMO` | `demo` | Sentry DSN of the shop |

The gateway serves the `test` environment without development mode: HTTPS only, behind the Coolify proxy, with a
`Secure` admin cookie. Its `demo` profile makes the demonstration public: the console accepts the published token
`demo-admin-token`, and the shop uses the published key `ofsp_test_DemoShopKeyPublishedForTheSimulator01`. The validator runs without development mode: it refuses private targets and signs with the
mounted key only. Configuring that key retires the key generated in development mode.

## Deployment order

1. Set `OPENFSP_APP_KEY` and `OPENFSP_VALIDATOR_ATTESTATION_SIGNING_KEY` on their Coolify stacks, and move
   `console.openfsp.org` to the `gateway` service and `simulator.openfsp.org` to the `simulator` service.
2. Push this repository, then redeploy the `gateway` and `validator` stacks.
3. Push [openfspht/openfsp](https://github.com/openfspht/openfsp).
4. Merge its release pull request.
5. Move the compose files to the new image version and push.

## Update

Every stack runs a pinned release of the images published on Docker Hub (`openfsp`), mirrored from GitHub Container Registry (`ghcr.io/openfspht`). Coolify deploys each one from this repository
on push: a new release reaches production when its version replaces the current one in the compose files, through a
Dependabot pull request or by hand, and rolling back means restoring the previous version.
